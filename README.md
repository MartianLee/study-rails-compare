# Is Rails slower than the others? — measure it, don't argue about it

Eight API servers. Four runtimes. One blog schema, one MySQL, one machine, one
load generator, three runs.

Everyone has an opinion about how much a framework costs you. Almost nobody has
a number. This repo is an attempt at a number that survives being argued with —
so the code, the schema, the seed data, the load generator and the raw results
are all here, and the fairness rules are written down before the numbers are.

**Read [`SPEC.md`](SPEC.md) before the results.** It is where the arguable
decisions live, and there are more of them than you would like.

---

## The question

Not "how fast is Rails". That question has no answer, because a Rails app and a
Go app are never doing the same work.

The question is narrower and answerable:

> Inside one runtime, how much do you pay for the framework and the ORM?

So every runtime here appears twice, doing byte-identical work:

| runtime | **full** — framework + ORM | **bare** — same server, raw SQL |
|---|---|---|
| Ruby | Rails 8.1 + Active Record | Rack + `mysql2` |
| Node | Express 4 + Sequelize 6 | `node:http` + `mysql2` |
| Python | Django 5.1 + Django ORM | WSGI + `mysqlclient` |
| Go | Gin + GORM | `net/http` + `database/sql` |

The pair shares a runtime, an HTTP server, a driver, a MySQL wire protocol, a
CPU limit and a machine. The **only** difference is the framework and the ORM.
Whatever falls out of the subtraction is the thing this repo calls the
**magic tax** — and because the subtraction happens inside one runtime, it does
not care that Go is faster than Ruby.

## Why a blog and not hello-world

A `hello world` benchmark measures a router. Nobody deploys a router.

The workload here is a blog list page — the single most common shape of endpoint
in a CRUD service:

```
GET /api/posts?page=3
  → 20 published posts, newest first
  → each with its author, its tags, and its comment count
  → 4 SQL statements, preloaded, no N+1
```

Plus a nested detail page (6 statements) and a write path that validates,
inserts and bumps a counter cache in one transaction. Against 500 users, 5,000
posts, 40,000 comments and 15,167 post/tag links.

## The fairness gate

Numbers from stacks that are secretly doing different work are worse than no
numbers. So before any measurement runs:

```sh
python3 harness/verify.py
```

boots each of the eight in turn and refuses to pass unless:

1. its JSON is **equal value-for-value** to the Rails app's, for both read endpoints
2. the SQL that reaches MySQL — read back out of MySQL's own `general_log` — is
   the statement set `SPEC.md` requires (4 for the list, 6 for the detail)
3. the write endpoint returns `201`, collapses whitespace, increments the counter
   cache, and returns `422` for a blank body

What MySQL actually saw, per stack, is committed in
[`docs/sql-emitted.md`](docs/sql-emitted.md). Check it rather than trusting this
paragraph.

## Results

Committed in [`docs/RESULTS.md`](docs/RESULTS.md), regenerated by
`harness/report.py` from `results/*.json`. Median of three runs, with the spread
next to every figure — a number whose spread is wide is a number you should not
argue from.

## Running it yourself

Requires Docker (any host — everything runs in Linux containers) and Python 3.

```sh
docker compose up -d mysql          # MySQL 8.4
./db/load.sh                        # generates seed.sql deterministically, loads it
docker compose build                # 8 app images + the load generator

python3 harness/verify.py           # the fairness gate — must pass
python3 harness/run.py --runs 3     # ~50 minutes; writes results/<mode>-run<N>.json
python3 harness/report.py           # -> docs/RESULTS.md
```

Useful subsets:

```sh
python3 harness/run.py --runs 1 --mode single --only rails,rails-bare
python3 harness/run.py --runs 3 --mode tuned
```

## Layout

```
SPEC.md                what every stack must implement, and every arguable decision
docker-compose.yml     mysql + 8 apps + the load generator, all CPU/memory limited
db/schema.sql          five tables
db/gen_seed.py         deterministic seed generator (fixed PRNG seed)
loadgen/main.go        the measuring instrument — ~190 lines, no dependencies
apps/<stack>/          the eight servers
harness/verify.py      the fairness gate
harness/run.py         the measurement campaign
harness/report.py      results/*.json -> docs/RESULTS.md
docs/RESULTS.md        the numbers
docs/sql-emitted.md    what MySQL actually saw, per stack
results/               raw per-run JSON
```

## Things this repo does not measure

Worth saying out loud, because a benchmark's silence is where its lies live:

- **Anything about developer productivity.** The whole reason a framework exists
  is missing from every number here. A magic tax of ×3 is not an argument
  against magic; it is the price tag on it.
- **Cold start, deploy, and boot under load.** Boot time is recorded, but a
  container starting on an idle machine is not a fleet rolling.
- **Real traffic shapes.** One endpoint at a time, uniform, no cache, no CDN, no
  background jobs, no fan-out to other services.
- **Bigger-than-memory data.** The whole dataset fits in the InnoDB buffer pool
  on purpose, so the measurement is of the app, not of the disk.
- **Any tuning of the frameworks.** Every stack is close to what its `new`
  command or its documentation gives you. A tuned Rails app and a tuned Django
  app would both land somewhere else.
